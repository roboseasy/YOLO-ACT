# YOLO-ACT 계획서

- 작성일: 2026-11-08
- 상태: 사용자 검토 대기
- 목표와 설계 근거: [기획서](yolo_act_proposal.md)

> **2026-11-11 변경:** 다음 두 부분은 새 명령으로 대체되었습니다. 단계, 게이트, 평가 절차는 그대로입니다. 명령은 [README](../README.md)에 있습니다.
> - M1 라벨러(`label_dataset.py`) → `lerobot-record-bbox`(녹화 중 bbox 기록)
> - M3 실행 스크립트(`eval_policy.py`) → `lerobot-rollout-bbox`
>
> LeKiwi는 LeRobot 0.6.0 CLI가 "리더 팔 + 키보드" 녹화와 바퀴 구동을 지원하지 않습니다. 그래서 LeKiwi용 bbox 녹화·평가 스크립트가 따로 필요합니다(아직 없음).

## 1. 환경

| 항목 | 값 |
| --- | --- |

| Python 환경 | conda `lerobot` (LeRobot 0.6.0, Ultralytics 8.4.138, Python 3.12) |
| LeRobot | `~/lerobot`, 커밋 `30da8e6`. 로컬 수정이 2개 파일에 있습니다 |
| 로봇 | `lekiwi06`, `roboseasy@192.168.0.206`, SSH 키 인증. ROS 2 Jazzy, `lekiwi_zmq_host` 포트 5555/5556 |
| 네트워크 | Wi-Fi 5 GHz. 베이스가 움직이므로 유선을 쓸 수 없습니다 |
| YOLO | `~/workspace/YOLO/outputs/runs/box-2/weights/best.pt` (yolo26n, 클래스 `box`). 재학습은 YOLO 저장소에서 합니다 |
| 녹화 | Physical Labs 앱의 데이터 수집. ROS 호스트의 영상 색을 맞게 처리합니다 |

**지켜야 할 규칙**

- Python은 로보시지 규칙서를 따릅니다. 들여쓰기는 탭, Boolean은 `is_`/`has_` 접두사, 타입 힌트, `BASE_DIR` 기준 경로를 씁니다.
- 현재 폴더는 git 저장소가 아닙니다. 코드 작성을 시작할 때 `git init`과 `develop` 브랜치를 만들고, 커밋은 `Tag: 한줄 설명` 형식을 씁니다.
- GitHub에 올린다면 레포 이름은 규칙상 `yolo_act`입니다.
- 비밀번호와 토큰은 문서와 코드에 적지 않습니다. 영상, 데이터셋, 가중치, `outputs/`는 git에 넣지 않습니다.
- 로봇 호스트에는 클라이언트를 하나만 붙입니다. 녹화와 평가 때는 `04.inference.py` 같은 다른 스크립트를 끕니다.

녹화 도구와 LeRobot은 고치지 않습니다.

합계는 약 8~9 작업일이며 추정치입니다. 재녹화나 YOLO 재학습이 생기면 늘어납니다.

## 4. 단계별 상세

### M0. 과제와 환경 고정

**할 일**

1. 놓는 위치를 정합니다. 팔이 닿는 로봇 몸체의 트레이 또는 로봇 옆 지점 중에서 고르고, 트레이라면 제작해 고정합니다.
2. 로봇 시작 위치와 상자 배치 구역을 바닥에 표시합니다. 평가용 상자 위치 10개를 정해 `configs/test_positions.json`에 적습니다.
3. 시작 자세의 정면 카메라에 상자 전체가 보이는 범위를 실측합니다. 접근이 끝난 자세의 손목 카메라에 상자가 들어오는지도 봅니다.
4. Physical Labs 데이터 수집으로 베이스 포함 시험 에피소드 2개를 녹화합니다.

**완료 조건**

- 시험 데이터의 `action`에서 `x.vel`이나 `theta.vel`이 0이 아닙니다.
- 저장 영상에서 상자는 갈색, 그리퍼는 보라색으로 보입니다.
- 팔이 움직이는 동안 `observation.state`가 그대로 반복되는 프레임이 5% 이하입니다. 기존 데이터는 2~3%입니다.
- 놓는 위치에 팔이 닿고, 상자를 놓았을 때 안정적으로 머뭅니다.

### M1. 라벨러 구현

**할 일**

- `bbox_features.py`: `BBoxExtractor`의 `reset()`, `update(frames)`, 차원 이름 상수. RGB에서 BGR로의 변환도 여기서만 합니다.
- `label_dataset.py`: 영상 디코딩, 프레임별 추출, 열 추가, 통계 재계산, 점검.
- `tests/test_bbox_features.py`: 정규화, 중심 계산, 최고 confidence 선택, 값 유지, 첫 검출 전 0, `reset`을 검증합니다.

**핵심 호출** (시험 데이터셋에서 동작 확인)

```python
info = {"dtype": "float32", "shape": [14], "names": FEATURE_NAMES}
labeled = add_features(
	source,
	{"observation.environment_state": (lambda row, ep, fi: env[int(row["index"])], info)},
	output_dir=output_dir,
	repo_id=repo_id,
)
recompute_stats(labeled)
```

2차원 배열을 그대로 넘기면 실패하므로 함수로 넘깁니다.
`recompute_stats` 직후에 `stats.json`의 `is_detected` 두 자리(인덱스 6, 13)만 평균 0.5, 표준편차 0.5로 고칩니다. 특징 제거, 학습, 체크포인트까지 그대로 전달되는 것을 확인했습니다.

**점검 리포트**: 가중치 경로와 sha256, conf, iou, imgsz, 카메라별 검출률, 여러 박스 비율, 최장 미검출 길이, 차원별 표준편차, 오버레이 영상 경로. 데이터셋 복사 과정에서 지워지지 않도록 `outputs/labels/<데이터셋>.json`에 저장합니다.

**완료 조건**

- 단위 테스트가 통과합니다.
- 프레임 수가 데이터셋과 정확히 같습니다.
- 좌표 차원의 표준편차가 모두 0.01 이상입니다. 미만이면 멈춥니다.
- 세 데이터셋으로 `lerobot-train`이 20 스텝 돕니다.
- 실험 2와 3의 체크포인트에 `encoder_env_state_input_proj`가 있고, 실험 2에는 백본이 없습니다.

### M2. 검출기 게이트

ACT 학습 전에 YOLO가 실제 작업에서 쓸 만한지 판단합니다. 검출이 나쁘면 이후 결과를 해석할 수 없기 때문입니다.

**재료**: 실제 작업 시연 10개, 상자가 없는 장면 1분, 멈춤과 이동이 섞인 영상.

**구간 구분**: 바퀴 명령이 있으면 접근, 바퀴 정지부터 그리퍼 닫기 전까지가 집기 직전, 그리퍼가 닫힌 뒤가 운반과 놓기입니다.

| 구간 | 카메라 | 기준 (초기값) |
| --- | --- | --- |
| 접근 | front | 상자가 보이는 프레임의 95% 이상 검출 |
| 집기 직전 | wrist | 상자가 보이는 프레임의 90% 이상 검출 |
| 운반과 놓기 | 둘 다 | 측정만 합니다 |
| 상자 없는 장면 | 둘 다 | 박스가 나오는 프레임 1% 이하 |
| 상자 1개 장면 | 둘 다 | 두 개 이상 잡히는 프레임 1% 이하 |

검출 유무는 자동으로 세고, 맞게 잡았는지는 오버레이 영상에서 구간별 100프레임을 사람이 확인합니다.

**코덱 차이 측정**: 같은 프레임의 JPEG 원본과 AV1 인코딩본에 YOLO를 돌려, 검출 일치율 95% 이상과 IoU 중앙값 0.9 이상을 봅니다.

**미달이면**: 놓친 프레임과 오검출 프레임을 `06.recollect_dataset.py` 또는 Roboflow로 YOLO 데이터에 더하고 `03.train.py`로 재학습합니다. 두 번 반복해도 미달이면 기준과 과제를 사용자와 다시 논의합니다.

**완료 시 고정**: 가중치 파일(sha256 기록), conf, iou, imgsz. 이후 바꾸면 라벨을 다시 만듭니다.

### M3. 실행과 평가 스크립트

`~/workspace/lekiwi-yolo/lekiwi-evaluate.py`를 복사해 시작합니다. 판정 키, 준비 동작, 일시정지, 리포트를 그대로 씁니다. 평가 도구가 실험 중 바뀌지 않도록 이 레포에 둡니다. 바꿀 곳은 다음과 같습니다.

1. **클라이언트:** `PYTHONPATH`에 `~/workspace/physical-labs-app`을 더하고 `ros_client_class()(LeKiwiClientConfig(...), liveness=None)`을 씁니다. GUI 없이 불러지는 것을 확인했습니다. `required_cameras`도 지정합니다.
   `make_lekiwi_client`는 쓰지 않습니다. 이 함수는 `liveness=None`이면 GUI 생존 표시를 쓰는데, GUI가 없으면 명령이 전부 버려집니다.
2. **bbox 주입:** `ds_features`에 `observation.environment_state`를 이름 14개와 함께 추가하고 관측 dict에 값을 넣습니다. LeRobot의 `build_dataset_frame`이 이름으로 꺼내 씁니다. 실험 2는 `ds_features`에서 영상 키를 뺍니다.
3. **행동 실행 길이:** `--n_action_steps`로 정책을 불러온 뒤 설정하고 `reset`합니다.
4. **이상 입력 정지:** 정규화된 bbox나 상태 값의 절댓값이 50을 넘으면 정지합니다. 기존 데이터의 바퀴 속도가 학습 데이터 안에서도 10.8까지 나오므로 기준을 더 낮추지 않습니다.
5. **단계별 시간 기록:** 켜고 끌 수 있는 옵션으로 YOLO, 정책, 1주기 시간을 남깁니다.
6. **기록 추가:** 위치 번호, 블록 번호, 실패 단계, 카메라별 검출률을 리포트에 넣습니다.
7. **에피소드 초기화:** 시작할 때 `BBoxExtractor.reset()`을 호출합니다.

**완료 조건**

- 저장된 에피소드 프레임을 실행 경로에 넣었을 때 14차원 값이 데이터셋과 1e-5 이내로 일치합니다.
- 명령 미송신 모드에서 60초 동안 평균 28 Hz 이상입니다.
- 이상 입력을 인위로 넣으면 정지합니다.
- `SPACE`, `ESC`, `Ctrl+C` 정지를 저속에서 확인합니다.

**YOLO를 동기로 호출하는 이유**: 제어 주기 안에서 직접 호출하고 별도 대기열을 두지 않습니다. 대기열이 없으면 오래된 프레임이 쌓여 지연이 커지는 일이 생기지 않습니다. 단계별 시간을 옵션으로 기록하면 30 Hz가 깨질 때 원인 단계를 바로 찾을 수 있습니다.

### M4. 파일럿 전 구간

본 데이터에 시간을 쓰기 전에 전체 흐름을 작은 규모로 끝까지 돌립니다.

**할 일**

1. 시연 30개를 녹화합니다.
2. 라벨링하고 세 데이터셋을 만듭니다.
3. 세 모델을 30,000 스텝 학습합니다. 약 3.7시간입니다.
4. `base_speed_scale=0.3`으로 첫 구동을 확인한 뒤 1.0으로 올립니다.
5. 모델마다 10회 평가합니다.

**여기서 정할 것**: `n_action_steps` 30 또는 temporal ensembling, 제한 시간(시연 평균의 2배 기준), 본 평가의 베이스 속도 배율, 시연 규칙 보완.

**완료 조건**

- 세 모델이 실물에서 끝까지 돕니다.
- 실험 1 또는 3이 10회 중 7회 이상 상자 앞까지 접근합니다. 미달이면 시연 품질과 파이프라인을 먼저 점검합니다.

파일럿 성공률로 과제 난이도를 판단하지 않습니다. 시연 30개의 결과로 100개의 결과를 알 수 없기 때문입니다. 그 판단은 M7 첫 반복에서 합니다.

**완료 시 고정**: 작업 정의, 시연 규칙, 카메라 각도, 캘리브레이션. 바뀌지 않았다면 파일럿 시연을 본 데이터에 포함합니다.

### M5. 본 데이터 수집

- 총 100개를 목표로 합니다.
- 상자 위치를 구역 안에서 무작위 순서로 둡니다. 학습기가 마지막 10% 에피소드를 검증에 쓰므로 순서에 치우침이 없어야 합니다.
- 실수한 에피소드는 앱의 재녹화 버튼으로 바로 다시 녹화합니다. 작업이 끝나면 시간을 기다리지 않고 저장 후 다음 에피소드로 넘깁니다.
- 세션이 끝날 때마다 라벨러를 돌려 점검 리포트를 봅니다. 검출률이 떨어지면 원인을 찾은 뒤 이어서 녹화합니다.
- 녹화 원본은 수정하지 않습니다. 라벨은 항상 새 데이터셋으로 만듭니다.

**완료 조건**: 점검 리포트의 차원 통계와 검출률이 정상이고, 오버레이 표본에서 이상이 없습니다.

### M6. 본 학습

5절 명령으로 세 모델을 같은 설정으로 학습합니다. 속도 측정 기준 예상 시간은 실험 1과 3이 각각 약 5.9시간, 실험 2가 약 42분입니다. 큰 데이터셋에서는 달라질 수 있습니다.

**체크포인트 선택**: 모델별로 10,000 스텝 체크포인트 중 검증 손실이 가장 낮은 것을 고릅니다. 검증 손실은 같은 모델 안에서만 비교합니다. 로봇 평가 **전에** 선택 결과를 `outputs/train/selected.json`에 기록하고 이후 바꾸지 않습니다.

### M7. 본 평가

6절 절차를 따릅니다. 첫 반복을 마치면 기획서 8절의 기준선 점검을 합니다. 포화나 바닥이면 나머지 반복을 진행하기 전에 정해진 조치를 합니다.

### M8. 분석과 보고

`docs/yolo_act_report.md`에 다음을 정리합니다.

- 모델과 조건별 성공률, Wilson 95% 신뢰구간
- 실험 3과 1의 Fisher 정확 검정 결과와 기획서 8절 기준에 따른 판단
- 단계별 실패 분포. 실험 2가 어디서 실패하는지 포함합니다
- 수행 시간, 검출률, 제어 주기
- 다음 결정: 도입, 추가 평가, 구조 변경 중 무엇을 할지

## 5. 명령

**세 번째 데이터셋 만들기.** 시험 데이터셋에서 같은 형식으로 동작을 확인했습니다.

```bash
lerobot-edit-dataset \
  --repo_id=HueyWoo/lekiwi_brownbox_bbox \
  --new_repo_id=HueyWoo/lekiwi_brownbox_bbox_only \
  --operation.type=remove_feature \
  --operation.feature_names="['observation.images.front','observation.images.wrist']"
```

**학습.** 스텝 수를 제외하고 같은 플래그 구성을 세 구성에서 20 스텝 돌려 확인했습니다. `--seed`는 기본값 1000을 명시한 것입니다.

```bash
conda activate lerobot

train() {  # train <출력이름> <데이터셋>
  lerobot-train \
    --dataset.repo_id="$2" \
    --dataset.eval_split=0.1 --eval_steps=10000 \
    --policy.type=act --policy.push_to_hub=false --policy.device=cuda \
    --policy.normalization_mapping='{"VISUAL":"MEAN_STD","STATE":"MEAN_STD","ENV":"MEAN_STD","ACTION":"MEAN_STD"}' \
    --steps=100000 --batch_size=8 --num_workers=8 --save_freq=10000 --seed=1000 \
    --wandb.enable=false \
    --output_dir="outputs/train/$1"
}

train exp1_img      HueyWoo/lekiwi_brownbox
train exp2_bbox     HueyWoo/lekiwi_brownbox_bbox_only
train exp3_img_bbox HueyWoo/lekiwi_brownbox_bbox
```

파일럿은 `--steps=30000 --save_freq=10000`으로 바꿉니다. 영상 증강은 세 실험 모두 끕니다(기본값).

포화로 시연 50개를 다시 학습할 때는 `--dataset.episodes`에 0~49를 목록으로 넘깁니다. 녹화 순서가 무작위이므로 앞의 50개를 씁니다. 코드에서 지원을 확인했지만 실행해 보지는 않았습니다.

## 6. 평가 절차

**사전 고정**: 체크포인트, `n_action_steps`, YOLO 설정, 성공 기준, 제한 시간, 위치 목록. 평가를 시작한 뒤에는 바꾸지 않습니다.

**기본 조건**: 시연과 같은 조명과 배경, 상자 방향 ±15°, 베이스 속도 배율 고정.

```text
위치 10개 × 3회 반복 × 모델 3개 = 90회
```

**순서**: 한 모델로 위치 10개를 도는 것을 한 블록으로 합니다. 반복마다 모델 순서를 돌립니다. 배터리와 조명 변화가 한 모델에 몰리지 않게 하기 위함입니다.

| 반복 | 순서 |
| --- | --- |
| 1 | 실험 1, 2, 3 |
| 2 | 실험 2, 3, 1 |
| 3 | 실험 3, 1, 2 |

**1회 진행**

1. 로봇을 시작 표시에 놓고 팔을 시작 자세로 맞춥니다.
2. 목록의 위치에 상자를 둡니다.
3. 실행합니다. 사람은 정지 키를 잡고 있습니다.
4. 성공 또는 실패를 입력합니다. 실패면 단계를 입력합니다: 접근, 집기, 놓기, 안전 정지.

**기록 필드**: `exp`, `seed`, `checkpoint`, `repeat`, `block`, `position_id`, `result`, `failure_stage`, `duration_s`, `front_detect_rate`, `wrist_detect_rate`, `yolo_ms`, `policy_ms`, `loop_hz`.

**운영 조건**: 노트북 전원을 연결합니다. 다른 클라이언트를 끕니다. 반복마다 로봇 충전 상태를 맞춥니다. 로봇 주변을 비웁니다.

**부 조건** (기본 조건을 마치고 시간이 되면, 위치 10개 × 1회 × 모델 3개 = 조건당 30회)

- 조명 변경
- 배경 변경 (상자류 제외)
- 상자 방향 무작위. 실험 2의 한계를 확인합니다

**재평가 규칙**: 기획서 8절 기준으로 판단 보류면 실험 1과 3을 다른 seed로 학습해 같은 절차로 30회씩 더하고, 합쳐서 한 번만 다시 판정합니다. 향상으로 판단한 경우에도 다른 seed로 학습한 실험 1과 3을 위치 10개씩 평가해 방향을 확인합니다.
